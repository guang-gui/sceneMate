## 1. 一句话结论

DeepSeek 的视觉能力**足够支撑 MVP 的"场景理解 + 建议生成"**，单次成本 ¥0.004、标签质量可用、JSON 结构稳定；但**延迟 2.3 秒**决定了它只能服务"用户主动上滑的抽屉"和"低置信难例复核"，实时站位框仍必须由端侧几何给出。

这不是限制，反而验证了 ADR-001 的判断：**端侧主链路、云端异步增强**。

### 3.2 输出样例（temperature=0，稳定复现）

```json
{
  "scene": { "label": "beach_sunset_portrait", "confidence": 0.92 },
  "lighting": { "label": "backlit", "confidence": 0.9, "lux_estimate": 320 },
  "subject": { "label": "person", "count": 1, "confidence": 0.95 },
  "tier": "strong",
  "instruction": { "actor": "subject", "direction": "left", "magnitude": "0.6m",
                   "text": "让她向左 0.6m" },
  "params": { "iso": 400, "shutter": "1/125", "ev": 0.7, "wb_k": 5600,
              "reason": "逆光主体欠曝，提升曝光补偿并降低 ISO 以保留天空高光" },
  "explain": { "before": "人物处于太阳正前方，脸部完全欠曝成剪影",
               "after": "人物向左偏移后太阳从侧后方露出，可保留轮廓光与面部细节",
               "mechanism": "侧逆光下入射光与镜头光轴夹角增大",
               "benefit": "主体曝光更均匀，减少死黑与天空过曝" },
  "risk": { "low_light": true,
            "advice": "逆光且环境亮度偏低，建议改用原生相机夜景模式辅助测光" }
}
```

值得注意的三点：
- **指令格式完全符合决策**：`actor=subject` + 第三人称「让她向左 0.6m」。
- **参数合理**：逆光欠曝 → ISO 降、EV +0.7、WB 5600，方向正确。
- **诚实降级到位**：主动提示「建议改用原生相机」，没有承诺画质——这正是 PRD R13 要的。

## 4. 三个必须记住的发现

### 发现 1：2.3 秒决定了它的位置

比 R01 的 800ms 预算高 3 倍，比 R02 的 1.5s 高 1.6 倍。**任何"每帧都问云端"的设计都不成立**。

它能服务的三件事：
1. 屏 2「场景分析抽屉」——用户主动上滑，可以接受 loading
2. 首次会话冷启动——端侧还没积累
3. 端侧置信 <0.6 的难例复核

### 发现 2：默认温度下，同一张图会给出互相矛盾的方向

| 调用 | tier | 指令 | 快门 | EV |
|---|---|---|---|---|
| 1 | weak | 让她**向右** 0.6m | 1/160 | 0.7 |
| 2 | strong | 让她**向左**半步 | 1/125 | 0.7 |
| 3 | strong | 让她**向左**半步 | 1/60 | 1.0 |

固定 `temperature=0` 后 4 次完全一致。

**架构含义**：LLM 输出是**不稳定信号**，必须三重约束——固定温度、按 `frame_hash` 缓存 30s、建议版本单调 + 最小展示 1.2s。否则取景框会左右乱跳，直接击穿 G2 信任目标。

### 发现 3：实验模型会下线

`deepseek-v4-flash-vision-exp` 2026-08-21 上线，两个月后即被 V4.1-Flash 接管，旧模型名只是别名。**模型名不能硬编码在业务代码里**，必须有 `ModelProvider` 适配层。

## 5. 集成设计（若采纳）

```
端侧                                    云端
─────────────────────────────────────────────────────
分割/姿态/几何 ──► 站位框（实时，不等云端）
     │
     ├─ 端侧场景分类（12ms）──► 三标签（立即可用）
     │
     └─ 用户上滑抽屉 / 置信<0.6
              │
              ├─ 720px JPEG (32KB) + 上下文 JSON
              ├─ 限流：20 次/日/设备，4 次/会话
              ▼
        deepseek-flash  (temp=0, thinking=off, json_object)
              │  2.3s
              ▼
        SuggestionSanitizer
          ├─ schema 校验（必填键、类型）
          ├─ 数值 clamp（ISO 100–6400、EV ±2.0、WB 2500–8000）
          ├─ 禁止词过滤（构图/光线/氛围/…）
          ├─ 置信度上限截断（无校准证据时 ≤0.85）
          └─ actor/文案模板校验
              ▼
        缓存（frame_hash → 结果，TTL 30s）
              ▼
        上屏（若已超时 → 丢弃，保留端侧建议）
```

**降级链**：云端超时 2.5s → 端侧规则建议 → 抽屉显示「离线分析」→ 不报错、不重试、不阻塞。

## 6. 成本模型（用实测单价重算）

| 场景 | 调用量 | 月成本 | 占 ARPU（¥0.32/DAU/月） |
|---|---|---|---|
| MVP：5,000 DAU × 0.5 次/日 | 2,500 次/日 | **≈¥300** | — （绝对值可忽略） |
| 规模化：5 万 DAU × 5% 会话 × 4 次 | 25,000 次/日 | ≈¥3,000 | **≈19%** |
| 失控：5 万 DAU × 100% 会话 × 4 次 | 500,000 次/日 | ≈¥60,000 | **≈375%** ❌ |

**结论**：
- MVP 阶段**成本可以忽略**，先验证价值，不要为省 ¥300/月去做自研。
- 规模化后必须收敛到 ≤5% 会话，否则吃掉全部毛利。
- 有个意外利好：DeepSeek 高峰是**工作日 9–12、14–18 点**，而日落场景（S1）在 18 点后、周末出游在全天——**拍照高峰与 API 高峰错开**，实际单价更接近空闲价 ¥0.0021。

## 7. 还不能回答的问题（需要真实照片）

本次只用了 1 张生成图，以下必须用真实拍摄集验证：

| # | 问题 | 验证方法 | 通过线 |
|---|---|---|---|
| 1 | 标签准确率 | 30 张真实照片（覆盖 S1–S5），人工标注对比 | top-1 ≥80% |
| 2 | 建议可用性 | 同一批图，3 名摄影师盲评「这条指令是否可执行」 | ≥70% 可用 |
| 3 | 多人/遮挡场景 | 合影 5 张、背影 3 张 | 不误判主主体 |
| 4 | 室内混合光（S3） | 餐厅暖光 5 张 | 不给出「降低色温」这类反向建议 |
| 5 | 稳定性 | 同图 10 次 temp=0 | 输出 100% 一致 |
| 6 | 帧间抖动 | 同一场景 5 帧连拍 | 方向翻转 ≤1 次 |

建议做法：**用 30 张真实照片跑一遍，人工打分，2 小时能出结论**。脚本已支持 `--json-out` 批量留档。

## 8. 合规提示（需法务确认，不阻塞 POC）

| 项 | 判断 |
|---|---|
| 数据出境 | DeepSeek 为境内服务，**不涉及出境**，比境外厂商简单 |
| 服务商资质 | 需确认其已完成生成式 AI 服务备案，并在合同中明确数据处理者角色 |
| App 侧披露 | 隐私政策需列明「第三方 AI 服务」及上传内容（压缩帧 + 设备上下文） |
| 上传内容 | 建议走 **L1 档（人脸模糊 + 640px）**，不要传原图；MVP 可先用 L0（仅标签+特征）验证 |
| 生成内容标识 | 输出是结构化建议、不直接展示生成文本给用户，标识义务较轻，但仍需法务确认 |
